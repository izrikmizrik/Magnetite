# Моддинг Magnetite

Magnetite — Minecraft: Java Edition 26.3 на Rust для ПК, Android и iOS. Ядро у всех трёх платформ
одно, ядро Horizon, поэтому мод пишется один раз и одинаково работает везде, где его вид мода
поддерживается. Этот гайд объясняет, какие бывают моды, как они устроены, что может мод, что
Magnetite добавил к Horizon и как выложить мод на площадку.

Полный список функций — [справочник](modding-reference.md): все хуки и все методы `Host`, по одной
строке о каждом. Подробная документация Horizon на английском лежит в `docs/modding/src` (книга
mdBook), ссылки на её страницы даны по ходу. English: [modding.en.md](modding.en.md).

## Виды модов

Любой мод — один файл `.hmod`: zip-архив с манифестом `horizon-mod.toml`, папками `assets/`
и `data/` и, если в моде есть код, этим кодом.

| Вид | Что внутри | Как работает |
| --- | --- | --- |
| **Контентный** | `assets/` и `data/`: блоки, предметы, рецепты, лут, теги, модели, текстуры, генерация мира | Игра читает его при запуске. Кода нет. |
| **WebAssembly** | `mod.wasm`, собранный из Rust | Игра запускает его в песочнице с ограничениями по времени и памяти. Компилятор у игрока не нужен. |
| **Lua** | Скрипты `data/<id>/scripts/*.lua` | LuaJIT, на всех платформах Lua 5.1. Сборка не нужна. |
| **Нативный** | Крейт на Rust, который собирается под конкретную сборку игры | Полная скорость и полное доверие. На ПК мод собирает лаунчер, на телефоны — ферма модов. |

WebAssembly и нативный мод пишутся на одном API, `mod_api` (крейт `horizon-mod-api`), с одними
и теми же хуками, частями, вложениями и зависимостями. Отличается только цель сборки. Lua-мод
вызывает те же хуки по их именам из того же каталога.

### Где какой мод работает

| Вид | ПК | Android | iOS с JIT | iOS без JIT |
| --- | --- | --- | --- | --- |
| Контентный | да | да | да | да |
| WebAssembly | да (Cranelift) | да | да (Cranelift) | да (интерпретатор Pulley, медленнее) |
| Lua | да (JIT) | да (JIT) | да (интерпретатор) | да (интерпретатор) |
| Нативный | собирает лаунчер | готовая сборка с фермы | готовая сборка, грузится напрямую | нет (или переподпись через ferrite-signer) |

На iOS LuaJIT всегда собран без JIT-компилятора, поэтому Lua там всегда интерпретируется.

Правило Magnetite: мир получается **бит в бит одинаковым** на ПК, на телефоне, с JIT и без него,
а без JIT игра не падает, а работает медленнее. Поэтому для новых модов основной путь —
**WebAssembly**: один `.wasm` на все платформы, без отдельных сборок. Нативный путь нужен для
тяжёлых модов (порты вроде Create), где важна каждая миллисекунда.

## Пакет и манифест

```text
mymod.hmod
├── horizon-mod.toml          # манифест: id, имя, версия, api, вид кода
├── assets/mymod/             # модели, текстуры, звуки, lang/ru_ru.json
├── data/mymod/               # блоки, рецепты, лут, теги, генерация
│   └── scripts/main.lua      # только у Lua-мода
└── mod.wasm                  # только у WebAssembly-мода
```

```toml
# horizon-mod.toml
id = "mymod"              # [a-z0-9_], до 64 символов: папка, журнал, ключ настроек
name = "Мой мод"
version = "1.0.0"
description = "Что делает мод."
authors = ["Ник"]
license = "MIT"
api = "0.2"               # версия контентного API

[lua]                     # только у Lua-мода
entry = "main.lua"
```

Таблицу `[wasm]` (хеш `mod.wasm` и версию тулчейна) пишет сборка WebAssembly-мода, руками её не
трогают. Версия SDK, под которую собран код, закрепляется в `Cargo.toml`
(`[package.metadata.horizon] sdk`).

Полное описание всех полей манифеста — `docs/modding/src/reference/manifest.md`.

Инструмент для создания и сборки модов — `cargo horizon-mod`:

```sh
cargo horizon-mod new mymod --template wasm     # новый WebAssembly-мод
cargo horizon-mod build --wasm                  # собрать mod.wasm и упаковать .hmod
cargo horizon-mod new mymod --template native   # новый нативный мод (на ПК его собирает лаунчер)
cargo horizon-mod update                        # перейти на новую сборку SDK
```

Пошаговые первые моды на английском:
- контентный: `start/first-content-mod.md`;
- нативный: `start/first-mod.md`;
- WebAssembly: `start/first-wasm-mod.md`.

## Как мод встраивается в игру

### Хуки

**Хук** — один момент игры: тик, сломанный блок, вход игрока. Мод реализует нужные ему хуки как
методы `mod_api::Hooks`, а игра вызывает каждый подписанный мод с **событием** этого момента и
**хостом** — типизированным доступом к игре.

```rust
#[derive(Default)]
struct MyMod;

#[mod_api::horizon_mod]
impl mod_api::Hooks for MyMod {
    fn register(&self, r: &mut dyn mod_api::Registrar, _: &mod_api::RegistrationContext) {
        // Один раз при запуске: ключи, части, настройки.
    }
}
```

У каждого хука есть **контракт**: от него зависит, что значит ответ мода.

| Контракт | Что делает мод | Ответ |
| --- | --- | --- |
| слушает (`listen`) | узнаёт о событии и может менять поля события | ничего |
| может отменить (`cancel`) | может запретить действие игры | `Flow::Cancel` останавливает действие и пропускает следующие моды |
| заменяет результат (`replace`) | может заменить ванильный ответ | первый мод, ответивший `Some`, побеждает |
| собирает ответы (`collect`) | добавляет свои записи | ответы всех модов складываются в список |

Моды вызываются по приоритету слушателя, выше — раньше, затем в порядке зависимостей. Мод,
которому нужно знать и об отменённых событиях, добавляет `receive_cancelled`:

```rust
#[listener(priority = 100)]
fn break_block(&self, host: &mut dyn ServerHost, event: &mut BreakBlockEvent<'_>) -> Flow {
    if self.protected(host, event.pos) { Flow::Cancel } else { Flow::Continue }
}
```

У хука есть **сторона**: сервер (логика мира), клиент (экран, рендер, звук, ввод) или обе.
Серверный хук работает и в одиночной игре: там сервер встроен в клиент.

### Части (Parts)

Когда момент относится к конкретному объекту, это метод **части**, а не глобальный хук. Часть
вешается на тип объекта в `register`, и игра зовёт её только для этих объектов.

| Часть | К чему вешается |
| --- | --- |
| `BlockPart` | тип блока, свой или ванильный |
| `BlockEntityPart` | блок с блок-сущностью (печь, сундук, машина) |
| `ItemPart` | тип предмета |
| `EntityPart` | тип сущности: моба, снаряда |
| `MenuPart` | тип меню (окна контейнера) |
| `FluidPart` | жидкость мода |

```rust
#[mod_api::horizon_part]
impl mod_api::BlockPart for Gauge {
    fn analog_output(&self, _: &dyn mod_api::LevelHost, event: &mut mod_api::AnalogOutputEvent) {
        event.output = 15; // компаратор у этого блока всегда видит 15
    }
}
// в register:
let stone = r.block_key("minecraft:stone");
r.block_part(stone, Gauge);
```

### Host

`Host` — всё, что хук может спросить у игры или сделать в ней: прочитать и поставить блок,
найти сущность, выдать предмет, отправить сообщение, сыграть звук. `ServerHost` доступен только
на сервере, `ClientHost` — только на клиенте, `Host` — на обеих сторонах. Объекты игры приходят
**хэндлами** (`LevelRef`, `EntityRef`, `PlayerRef`...): хэндл читается через хост, а устаревший
хэндл даёт `None`, а не падение.

### Фазы загрузки

Код мода выполняется по фазам, и в каждой доступно своё:

| Фаза | Что доступно |
| --- | --- |
| Packages | поиск пакетов, без хоста |
| Registration | объявления через `RegistrationContext`: ключи, части, настройки; без хоста |
| Setup | чтение ассетов, данных и реестров; без мира |
| Config | настройки и файлы конфигурации мода |
| Reloading | перезагрузка данных (`/reload`, смена ресурспаков) |
| World | полный `ServerHost` или `ClientHost` |

### Кроме готовых хуков: `[[inject]]` и мод-библиотеки

- **`[[inject]]`** вешает типизированного слушателя на функцию игры без компиляции кода игры:
  `head` (до тела: поменять аргументы, отменить вызов или подставить результат), `return` (после
  тела: поменять возвращаемое значение) или `replace` (функцией целиком владеет мод). Точки есть у
  функций модуля `game/` крейта `horizon-client` и у отмеченных `#[replaceable]` ниже. Работает для
  нативных и WebAssembly-модов; WebAssembly-мод с `[[inject]]` пересобирается под каждую новую
  сборку игры. Подробно — `concepts/injections.md`.
- **Мод-библиотека** публикует свои функции и хуки для других модов: они указывают её в
  `[dependencies]` и вызывают обычным Rust-кодом (`my_library::function()`). Игра грузит одну
  копию библиотеки на все моды, которые ей пользуются.
- **Нативный путь** (`[[native.mixin]]`, `[[native.loop]]`, `[[native.bridge]]`,
  `[[native.module]]`) меняет код внутри функции. Только для нативных модов.

На телефонах точки `[[inject]]` есть только в сборке игры, подготовленной как SDK; APK и IPA пока
так не собираются, поэтому мод с `[[inject]]` сейчас работает только на ПК.

Подробнее о хуках, частях, фазах, вложениях (attachments), возможностях (capabilities) и
транзакциях — в разделе Concepts английской книги.

## Что Magnetite добавил к Horizon

Эти возможности сделаны по ТЗ ядра для портов модов (Farmer's Delight, Create). Они работают
одинаково для нативных, WebAssembly- и, где сказано, Lua-модов.

### Преобразование данных при загрузке

До того как игра разберёт файлы данных, мод может прочитать их и переписать: добавить, удалить
или изменить записи. Так собственные форматы мода превращаются в те, что игра читает, без правки
датапака.

```rust
r.register_data_transform(mod_api::DataFiles::BIOME_MODIFIER, MyFilterModifiers);
```

| Вид | Какие файлы | Когда |
| --- | --- | --- |
| `DataFiles::BIOME_MODIFIER` | `data/<ns>/neoforge/biome_modifier/` всех модов | при открытии мира, когда биомы и теги уже загружены |
| `DataFiles::RECIPE` | `data/<ns>/recipe/` | при каждой загрузке и `/reload` |

Пример: модификатор `farmersdelight:add_features_by_filter`, который игра не знает, переписывается
в `neoforge:add_features` с явным списком биомов. Рецепт с OR-группой ингредиентов разбивается на
отдельный рецепт на каждый вариант.

Правила:
- преобразования идут в порядке загрузки модов, каждое видит результат предыдущего;
- преобразование — чистая функция входа: без часов, случайности и чтения файлов, файлы приходят
  и уходят отсортированными по id;
- ошибка или паника пишется в журнал с id мода, а файлы остаются как были.

### Свои рецепты верстака

Рецепт с собственным сериализатором отвечает на три вопроса: подходит ли сетка (`matches`), что
получится (`assemble`) и что останется в сетке после крафта (`remaining_items`).

```rust
r.register_crafting_recipe_serializer("my_mod:dough", Dough);
```

`remaining_items` возвращает на каждую ячейку `Some(стак)` или `None` (обычный остаток предмета).
Остаток возвращается в освободившуюся ячейку, как ведро воды после теста. Это работает в сетке
2×2 инвентаря и 3×3 верстака, при shift-клике — на каждый крафт. Колбэки обязаны быть чистыми:
они же считаются в предсказании клиента. Для машины, которая сама читает свои рецепты, есть
`register_recipe_type` и `register_raw_recipe_serializer`. Подробно —
`docs/modding/src/crafting-recipe-kinds.md`.

### Тик блок-сущности знает свой мир

`block_entity_tick` получает `level` — мир, в котором тикает блок-сущность. Станции мода
работают в Незере и Энде так же, как в обычном мире. Пишите в мир через `level`, а не через
хэндл фиксированного измерения.

### Предмет в руке можно менять

В `use_item_on` (части блока) событие несёт `used` — стак, которым кликнули. Мод может заменить
его, поменять количество или компоненты (`stack_mut`), и игра положит результат в руку после
вызова. Пример: сковорода забирает яйцо и отдаёт пустую руку или другой предмет.

### `/reload` для таблиц модов

Таблицы рецептов машин мода строятся в `tags_updated` при загрузке серверных данных. Хук
вызывается после каждой загрузки и каждого `/reload`, даже когда на сервере никого нет, и
`recipes_of_type` читает уже новую таблицу. Серверные слушатели перезагрузки регистрируются в
`add_server_reload_listeners`.

### `copy_components` в луте

`minecraft:copy_components` с `"source": "block_entity"` переносит компоненты сломанной
блок-сущности мода в дроп: её сохранённые `components` и те, что мод отдаёт через хук части
`block_entity_collect_components`. Кастрюля сохраняет имя и еду, когда её ломают.

### Торговля из пространства имён мода

`data/<ns>/villager_trade/` и `trade_set` мода теперь читаются из его собственного пространства
имён. Профессия может покупать урожай мода, странствующий торговец — продавать его семена.

## Lua-моды

```toml
[lua]
entry = "main.lua"
```

Скрипты лежат в `data/<id>/scripts/*.lua`. `entry` выполняется при запуске игры,
`require("util")` грузит `util.lua` из той же папки. `/reload` перечитывает скрипты в новом
состоянии.

```lua
-- Глобальный хук.
horizon.on("loot_table_load", function(id, table)
  if id == "minecraft:chests/simple_dungeon" then
    table.pools[#table.pools + 1] = { rolls = 1,
      entries = { { type = "minecraft:item", name = "mymod:onion" } } }
  end
  return table
end)

-- Часть блока: ctx.used — стак в руке, его можно изменить, заменить или убрать (nil).
horizon.block("mymod:skillet", {
  use_item_on = function(ctx)
    if ctx.stack and ctx.stack.id == "minecraft:egg" then
      ctx.used = { id = "mymod:skillet_with_egg", count = 1 }
      return "success"
    end
  end,
})

-- Часть блок-сущности: ctx.data (слоты данных) и ctx.nbt меняются, ctx.dimension — её мир.
horizon.block_entity("mymod:stove", {
  block_entity_tick = function(ctx) ctx.data[1] = ctx.data[1] + 1 end,
})

-- Преобразование данных и свой рецепт.
horizon.data_transform("biome_modifier", function(files, context) return files end)
horizon.crafting_recipe("mymod:dough", {
  matches = function(recipe, grid) return true end,
  assemble = function(recipe, grid) return { id = "mymod:dough", count = 1 } end,
  remaining_items = function(recipe, grid) return {} end,
})
```

Из контекста хука можно читать мир: `ctx.block_at(x, y, z)` и `ctx.biome_at(x, y, z)`.

Пока Lua доступны хуки `loot_table_load`, `tags_updated`, `use_item_on` и `block_entity_tick`,
плюс преобразования данных и свои рецепты. Имя любого другого хука — ошибка при загрузке скрипта
с объяснением: такого хука нет или он ещё не открыт для Lua. Список будет расти, имена те же, что
в [справочнике](modding-reference.md).

**Надёжность.** Каждый вызов скрипта защищён: ошибка пишется в журнал с id мода, файлом и
строкой, игра продолжает работу. После `max_errors` ошибок подряд хук выключается до `/reload`.
Вызов дольше `budget_ms` пишется в журнал, а дольше `hard_limit_ms` — останавливается.
Настройки — `config/horizon-lua.json` в папке игры:

```json
{ "max_errors": 5, "budget_ms": 2, "hard_limit_ms": 500, "jit": "auto", "allow_io": false }
```

**Особенности LuaJIT (Lua 5.1).** Числа — только double, целого типа нет. Нет `//` и побитовых
операторов, вместо них `bit.band` и другие функции `bit`.

## Детерминизм

Всё, что участвует в загрузке данных и генерации мира, должно давать один и тот же результат на
любой машине:
- никаких часов, `math.random` и чтения файлов в преобразованиях, генерации и колбэках рецептов;
- в Lua случайность только `horizon.random(seed)` (тот же генератор, что `java.util.Random`), а
  обход таблиц — `horizon.sorted_pairs(t)`, потому что порядок `pairs()` меняется от запуска к
  запуску; `os` и `io` выключены, пока не разрешены в конфиге;
- в Rust — отсортированные коллекции (`BTreeMap`, `Vec`) там, где порядок влияет на результат.

## Ограничения на телефонах и в песочнице

- **WebAssembly:** нет файловой системы, потоков, прямого доступа к GPU, своих генераторов чанков
  и миксинов. Вместо миксинов — точки `[[inject]]`. Расширение WebAssembly-API (генераторы
  чанков, своя папка мода, параллельные вызовы, безопасный шейдерный API) запланировано.
- **Нативные моды на телефоне** — только готовые сборки под точную версию игры и платформу:
  компилировать на телефоне нельзя. Нет сборки для вашей версии — мод не ставится, и площадка так
  и пишет.
- **iOS без JIT:** нативные моды недоступны (или переподписываются через ferrite-signer),
  WebAssembly идёт через Pulley, Lua — через интерпретатор. Будущее поле манифеста
  `ios_jit = "required" | "recommended" | "optional"` скажет, нужен ли моду JIT.

## Касания для модов (запланировано)

Мод будет получать касания экрана на всех платформах, включая ПК с сенсорным экраном: id пальца,
фазу (начало, движение, конец, отмена), координаты и силу нажатия, если устройство её даёт. Мод
сможет «забрать» касание у тач-управления игры. Порядок: экран мода → HUD модов → тач-управление
игры. Кнопки раскладки уже сейчас могут нажимать клавиши модов.

## Площадка модов Magnetite

Моды раздаются через площадку [izrikmizrik/magnetite-mods](https://github.com/izrikmizrik/magnetite-mods).
Игра и лаунчер телефона читают её индекс `https://izrikmizrik.github.io/magnetite-mods/index.json`
(формат реестра Horizon, schema 1), а файлы модов лежат в релизах репозитория.

Запись мода в индексе:

```json
{
  "id": "mymod", "kind": "mod", "name": "Мой мод", "summary": "Одна строка.",
  "description": "Markdown.", "authors": ["Ник"], "license": "MIT",
  "source": "https://github.com/ник/mymod", "categories": ["utility"], "tags": ["hud"],
  "versions": [{
    "version": "1.0.0", "published": "2026-11-23", "changelog": "",
    "api": "0.2", "side": "both", "capabilities": ["registries"], "game": "26.3",
    "file": { "name": "mymod-1.0.0.hmod",
              "url": "https://github.com/izrikmizrik/magnetite-mods/releases/download/mymod-1.0.0/mymod-1.0.0.hmod",
              "size": 12345, "sha256": "…" }
  }]
}
```

- `kind`: `mod` — контентный, WebAssembly или Lua; `native-mod` — нативный; есть ещё `modpack`,
  `resourcepack`, `shader`, `shaderpack`, `datapack`.
- Каждая версия закреплена SHA-256 файла. Если у проекта есть ключ minisign, каждая версия
  подписывается им.
- Готовые сборки нативных модов под Android и iOS — поле версии `native_binaries`: записи
  `build` (точный id сборки игры), `target` (`aarch64-linux-android`, `aarch64-apple-ios`) и
  `file`. Их кладёт ферма модов. Собираются только моды, чья лицензия разрешает раздачу бинарников.

Чтобы выложить мод: опубликуйте `.hmod` в релизе своего репозитория или пришлите его в
magnetite-mods и откройте pull request с записью в `index.json`. Полный формат индекса —
`docs/modding/src/reference/registry-index.md`.

В игре моды ставятся так:
- на ПК: Настройки → Моды → Найти моды;
- на телефоне: лаунчер → Моды → Найти моды.

WebAssembly-, Lua- и контентные моды ставятся и включаются сразу, а загружаются при следующем
запуске игры.
